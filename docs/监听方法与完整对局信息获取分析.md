# 雀魂运行时监听方法与完整对局信息获取分析

整理日期：2026 年 10 月 4 日。适用对象：本机「雀魂麻將」Safari 网页 App，页面为 https://game.maj-soul.com/1/ 。

本次已经验证：能够在正在运行的牌局连接上被动接收消息，解析出座位、自己的新摸牌、各家的弃牌、碰牌和拔北。仅从局中新增消息监听器，不能自动补回已经发生的事件。要在中途接入后建立完整的当前局面，需要另取可信的初始状态，再接续实时事件；服务器恢复消息是有协议依据的候选途径，但本机尚未完成恢复流程实测。

本文把“已实测”“协议或实现支持”“仍需验证”分别标明。这里的完整当前局面主要指本人手牌和桌面公开信息；它不等于整场历史，也不包括尚未向本机公开的对手手牌和牌山。

**重现监听的方法**

1. 保持游戏运行。在 Safari 的“开发”菜单进入“检查 App 和设备”，选中「雀魂麻將」下的 `game.maj-soul.com — 1`。实际菜单文字可能因 Safari 版本而异。
2. 在该目标的控制台枚举现有 WebSocket。`queryInstances` 是 Web Inspector 提供的控制台函数，不是普通网页 JavaScript API，不能直接把它当作网页脚本的内置函数。[WebKit 控制台文档](https://webkit.org/web-inspector/console-command-line-api/)
3. 对已确认的游戏连接增加 `message` 监听器，复制收到的字节，在本地保存后离线解码。
4. 导出后移除监听器。关闭检查器本身不应替代明确的停止和清理操作。

先检查连接概况，避免把大厅连接当作牌局连接：

```javascript
queryInstances(WebSocket).map(s => ({
  url: new URL(s.url).origin + new URL(s.url).pathname,
  readyState: s.readyState,
  binaryType: s.binaryType
}))
```

以下是本次验证所使用的临时监听逻辑。它只适合短时取样：90 秒后停止、最多保留最近 60 条、只接收小于 1 MiB 的 ArrayBuffer 消息。本次目标的 `binaryType` 已确认是 `arraybuffer`。这些限制意味着它不是完整对局记录器。

```javascript
(() => {
  if (window.__mjRuntimeAudit) return 'probe already exists';
  const sockets = queryInstances(WebSocket).filter(s =>
    s.readyState === 1 &&
    new URL(s.url).pathname === '/game-gateway-zone'
  );
  const p = { frames: [], sockets };
  p.listener = e => {
    if (e.data instanceof ArrayBuffer && e.data.byteLength < 1048576) {
      p.frames.push({
        time: Date.now(),
        bytes: new Uint8Array(e.data.slice(0))
      });
      if (p.frames.length > 60) p.frames.shift();
    }
  };
  p.stop = () => sockets.forEach(s =>
    s.removeEventListener('message', p.listener)
  );
  window.__mjRuntimeAudit = p;
  sockets.forEach(s => s.addEventListener('message', p.listener));
  p.timer = setTimeout(p.stop, 90000);
  return JSON.stringify({ attached: sockets.length, autoStopSeconds: 90 });
})()
```

本次返回 `attached: 1`。若返回 0，说明没有匹配连接，需要检查目标和连接路径；若有多条，须按连接分别记录和验证，不能把不同对局的动作混合排序。

停止并把原始样本复制到剪贴板，可在同一控制台执行：

```javascript
(() => {
  const p = window.__mjRuntimeAudit;
  if (!p) return 'no probe';
  p.stop();
  clearTimeout(p.timer);
  const data = p.frames.map(f => ({
    time: f.time,
    hex: Array.from(f.bytes, b => b.toString(16).padStart(2, '0')).join('')
  }));
  copy(JSON.stringify(data, null, 2));
  return { copiedFrames: data.length };
})()
```

将剪贴板内容保存为新样本的 `capture.json`，确认成功后执行 `delete window.__mjRuntimeAudit`。`copy` 同样是 Web Inspector 控制台提供的函数。本次现场采用分段控制台导出取得了相同的数据结构；上述剪贴板导出是据该结构整理的便捷写法，没有在本机重新进行现场采样。不要覆盖已经保存的验证样本。

**从原始消息得到牌值**

实测处理路径是：WebSocket 消息字节 → 消息封装 → ActionPrototype → 动作数据还原 → 对应动作的 Protobuf 字段 → 牌局状态更新。

通知消息以 `0x01` 开头，随后是 Protobuf Wrapper；Wrapper 的名字为 `.lq.ActionPrototype` 时，内部给出动作序号、动作名称和数据。请求及响应使用 `0x02`、`0x03`，并多出两字节的小端请求编号，不能统一按通知格式剥头。[消息封装实现](https://github.com/Apricot-S/majsoulrpa/blob/13698e226eace210ff8772fcabacfd2916299c4e/src/majsoulrpa/sniffer/envelope.py)

实时 ActionPrototype 的内层数据使用以下还原算法。变量 `data` 是动作数据本身，不是整个 WebSocket 消息，也不是 Base64 文本。

```python
keys = (132, 94, 78, 66, 57, 162, 31, 96, 28)
plain = bytes(
    value ^ (((23 ^ len(data)) + 5 * i + keys[i % 9]) & 255)
    for i, value in enumerate(data)
)
```

该算法已在本次 48 条真实动作上验证。随后按相应消息类型解析 Protobuf；例如弃牌和摸牌的字段 1 是座位，字段 2 是牌值，但不能把这一对应关系推广到所有消息类型。`m/p/s/z` 分别表示万、筒、索、字牌；`2z` 为南风，`6z` 为发财。红五应保留独立牌值，不能在原始记录阶段与普通五合并。

尤其要区分来源：参考实现对实时动作启用还原，对恢复动作 `decode_restore_action` 关闭还原。不能对恢复消息中的动作再次 XOR。本次已实测的是实时路径；恢复路径的依据来自源码，仍待本机样本验证。[动作解码实现](https://github.com/Apricot-S/majsoulrpa/blob/13698e226eace210ff8772fcabacfd2916299c4e/src/majsoulrpa/screens/match/_action.py)

已有的 `decode_sample.py` 只输出本次四类动作的选定字段，不是完整协议解码器。新增的 `extract_actions.py` 只从原始入站通知提取 ActionPrototype，也不负责解码恢复响应、开局手牌、结算或完整状态。

**随时开始能否获得所有信息**

| 希望取得的内容 | 仅从此刻新增监听 | 可补齐的途径与条件 |
| --- | --- | --- |
| 接入后发生的本人摸牌、公开弃牌和副露 | 已实测可获取样本覆盖的动作 | 还需处理换连接、其他动作类型和持续保存 |
| 当前完整本人手牌及桌面公开状态 | 不能保证 | 先取得客户端状态或有效恢复基线，再接实时动作 |
| 当前小局此前完整动作顺序 | 不能保证 | 恢复包若包含从开局开始的完整动作序列，才可补齐 |
| 当前整场比赛此前各小局历史 | 不能保证 | 需要此前持续记录，或服务端实际提供的完整牌谱 |
| 对手尚未公开的手牌、未来牌山 | 本次消息没有提供 | 不能靠解析空字段补出；本次没有支持实时获取的证据 |

标准 WebSocket 接口提供收到消息时的事件，没有供后来监听器查询完整历史消息的接口。因此，“从现在开始加监听”本身不会重放已经分派的消息。开发者工具或应用自行保留的记录是额外数据源，也不能假设它们从开局就存在。[WebSocket 标准](https://websockets.spec.whatwg.org/#feedback-from-the-protocol)

当前状态与完整历史也不同。例如两条不同的摸切历史可能产生相同的当前手牌与牌河；只拿到快照，不能唯一还原所有历史摸牌、操作耗时和全桌动作的交错顺序。这是信息缺失造成的限制。

**局中恢复最值得验证的途径**

协议定义中的 `FastTest.enterGame` 与 `FastTest.syncGame` 均有恢复响应。其 `game_restore` 结构可以容纳状态快照及动作列表；同步请求还带有小局标识和动作序号。快照字段覆盖本人手牌、宝牌指示牌、各家分数、弃牌和副露。这是“先恢复当前状态，再继续监听”的具体依据。[恢复协议定义](https://github.com/Apricot-S/majsoulrpa/blob/13698e226eace210ff8772fcabacfd2916299c4e/src/majsoulrpa/assets/protocol/liqi.proto)

这些定义来自社区项目的协议文件，并非官方服务端保证。不能仅凭字段存在就断定每次请求都会填满快照、从第 0 步补发，或返回整场比赛。可能只返回相对某个已知步骤的增量；旧小局是否保留、是否仍在局内，以及该请求上下文，都需要实际响应证据。

这里还有三个实施细节：

1. **需关联请求和响应。** 响应封装可能没有方法名，只保留请求编号。仅监听入站通知足以验证实时动作，但要可靠辨认恢复响应，需要被动记录对应出站请求的方法名与编号，或在客户端已经关联完成的解码层读取结果；不能凭几个相似字段猜测它是恢复包。[请求响应关联实现](https://github.com/Apricot-S/majsoulrpa/blob/13698e226eace210ff8772fcabacfd2916299c4e/src/majsoulrpa/sniffer/correlator.py)
2. **监听要覆盖新连接。** 本文临时脚本只绑定当时已有的 WebSocket。刷新会重建页面，重连可能新建连接，旧监听器不会自动迁移。要观察正常重新进入游戏时的恢复消息，需要在请求发生之前覆盖新连接；加载后再枚举连接可能已经错过恢复包。自动方案需验证文档启动阶段的安装和新连接捕获，不能把旧脚本加上刷新就称为完成恢复。
3. **快照和实时动作必须按同一时间点衔接。** 应先缓存新增动作，再载入可信基线，按恢复语义应用补发动作，并使用对局、小局、动作序号去重。只有确认连续、没有缺口，才标记为完整。快照对应哪一步、补发动作处于快照前还是后，应通过实际样本验证，不能一律重复应用。

如果保持纯被动，可以等待游戏自然发生同步或重连，但没有即时完成的保证。主动调用同步或强制重连会改变运行过程；本次只做分析，没有执行这两类操作。社区 Unity 实现也区分累积状态查询与强制重连恢复，不能把一个名为“同步”的函数当作无副作用的内存读取。[Unity 实现记录](https://github.com/Sunalamye/Naki/blob/main/docs/majsoul-unity-protocol.md)

**其他途径的适用范围**

直接读取客户端内存中的状态，理论上可以在局中取得已用于画面展示的信息，无须回放之前每个网络包。本机已经能访问 Unity 的内存接口，但尚未定位出稳定的手牌及牌河数据结构；“能读到内存”不等于“能直接读出完整局面”。这条路线仍需逆向对象布局、版本适配和与画面逐项核对，且不保证内存保留完整动作历史。

画面识别或人工录入可以为当前可见手牌、牌河和副露建立基线，适合临时补齐，但会受到遮挡、动画、红牌、旋转牌和被鸣牌的弃牌标记影响，也不能恢复画面未保留的历史。此路线本次没有自动化验证。

对局结束后的牌谱是核对整场历史的另一来源。牌谱协议与实战消息有不同结构，可表示各家起手牌及后续记录；应只按用户可访问、服务端实际返回的牌谱解释完整性，不能推断进行中的比赛立即可取，也不能把牌谱字段当作实时暗牌已经发给本机的证据。[牌谱协议定义](https://github.com/Apricot-S/majsoulrpa/blob/13698e226eace210ff8772fcabacfd2916299c4e/src/majsoulrpa/assets/protocol/liqi.proto)

若希望使用者随时打开查看工具就有完整数据，最可靠的设计是让记录器在牌局开始前持续采集并落盘，查看界面可以晚开。这满足“随时查看”，不等于记录器首次启动于任意时刻也能获得过去全部数据。运行中的中途接入则需要额外的恢复基线。

**建议的后续实现和验收标准**

优先实现“恢复基线加连续实时事件”，同时分别记录 `current_state_complete` 与 `history_complete`，不要用一个完整标记涵盖两种不同保证。没有可信基线时展示已知数据和缺失范围；遇到动作序号缺口、未知动作或连接变化时，不继续宣称状态完整。

正式记录器应去掉“只留最近 60 条”的滚动丢弃策略，改为按连接、对局及小局分段持久化，报告无法保存或解析的消息，处理自己的碰杠消耗牌、拔北、立直、宝牌变化和小局切换。需区分“曾被打出过的牌”和“当前仍在牌河中的牌”，防止被鸣走的牌在牌河和副露重复计数。

下一次验证应在可控的测试对局中进行：先建立从开局开始的参考记录；在局中另启动采集，并捕获正常恢复流程；逐项比较本人手牌、各家牌河、副露、分数、宝牌和剩余牌数。如果恢复包提供历史动作，还要比较起始步骤、顺序和缺口。仅拿到响应或显示了几张牌，不能算通过“任意时刻完整恢复”的验收。
