# Maj-Soul++ 运行时监听与信息完整性

本文描述当前 Python / WebKit 应用的监听架构，以及中途进入对局时能够确认的信息范围。这里的“完整当前局面”指本人手牌和桌面公开信息，不包括对手未公开手牌、未来牌山或整场比赛的完整历史。

## 当前架构

```text
WKWebView 打开雀魂页面
  → 页面加载前安装采集器
  → 被动接收牌局 WebSocket 消息
  → 解码动作并更新本小局状态
  → WKScriptMessageHandler 原生消息通道
  → Python 写入本地统计日志并更新窗口浮层
```

[monitor.py](../src/monitor.py) 创建独立的系统 `WKWebView`，在主页面的文档启动阶段注入 [core.cjs](../src/core.cjs)、[browser.js](../src/browser.js) 和 [overlay.js](../src/overlay.js)。采集器包装页面的 `WebSocket` 构造入口，为后续创建的牌局连接增加监听器；每条连接按接收顺序处理消息。

当前采集器以 `/game-gateway` 开头的连接路径筛选候选牌局连接，再通过 `.lq.ActionPrototype` 等消息确认并处理对局数据。路径和协议是客户端实现细节，游戏更新后仍可能需要适配。

采集器被动观察游戏原有的出站请求，将 `FastTest.enterGame`、`FastTest.syncGame` 的请求编号与方法名对应起来，以识别随后收到的恢复响应。游戏原有的发送方法按原参数调用；采集器不自行请求同步、不发牌局操作，也不主动触发重连。

统计快照通过 `window.webkit.messageHandlers.mjStatistics.postMessage` 进入 Python。原生接收端检查消息来自主 frame 的 `https://game.maj-soul.com`，再写入本地日志并更新浮层。运行数据位于 `~/Library/Application Support/Maj-Soul++/`，不写入应用包。

## 消息解码与状态更新

解码流程为：WebSocket 字节 → 消息封装 → `ActionPrototype` → 动作数据还原 → 对应动作的 Protobuf 字段 → 状态更新。

- `0x01` 表示通知，随后为 Protobuf Wrapper。
- `0x02`、`0x03` 表示请求、响应，还带有两字节的小端请求编号。
- 实时 `ActionPrototype` 的动作数据需要先还原；恢复响应中的动作使用明文 Protobuf，不能再次执行还原。

实时动作的内层数据按以下规则还原，`data` 指动作数据本身，不是整条 WebSocket 消息：

```python
keys = (132, 94, 78, 66, 57, 162, 31, 96, 28)
plain = bytes(
    value ^ (((23 ^ len(data)) + 5 * i + keys[i % 9]) & 255)
    for i, value in enumerate(data)
)
```

动作字段按消息类型分别解析。`m/p/s/z` 分别表示万、筒、索、字牌；原始牌值保留赤五与普通五的区别，仅在已知牌数量汇总时合并同牌型。

当前状态处理覆盖开局发牌、摸牌、弃牌、吃碰杠、拔北、和牌、流局，以及相关消息中的宝牌、分数和立直成立信息。立直宣言与立直成立分开处理：只有服务器确认成立才标记“已立直”，下一小局发牌或整场结束时清除。

每次 `ActionNewRound` 建立新的本小局基线并刷新浮层；之后每个接受且未重复的动作都刷新，不限于本人回合。动作序号用于去重和缺口检查，被鸣走的弃牌保留历史标记，但计数时不与副露重复累加。小局结束保留最新状态，整场结束清空当前统计及计数。

## 能否在任意时刻启动并获取所有信息

**不能保证。** 自动启动监听解决的是从页面加载开始持续采集；它不意味着服务器一定会补发监听前的全部信息。应用打开的是独立窗口，也不会读取另一 Safari 窗口已经收到的历史消息。

| 需要的信息 | 当前可以取得的条件 | 边界 |
| --- | --- | --- |
| 启动后发生的本人摸牌、公开弃牌和副露 | 当前窗口收到相应动作，且协议解析成功 | 序号缺口或未知动作会降低完整性 |
| 当前完整本人手牌和本小局公开状态 | 捕获开局基线后连续处理动作；或取得可核对的恢复基线 | 恢复快照与补发动作的边界尚不能一概保证 |
| 本小局此前完整动作顺序 | 服务端恢复动作确实包含从开局起的完整连续序列 | 仅有当前快照不能还原全部历史顺序 |
| 整场此前各小局历史 | 应用此前已持续记录，或另有服务端实际提供的完整牌谱 | 当前状态会在新小局及整场结束时重置，本地日志另行保留 |
| 对手未公开手牌、未来牌山 | 当前被动监听没有提供这类信息的依据 | 不能由空字段、当前快照或已知牌计数补出 |

WebSocket 的新增监听器接收后续事件，不会自动重放已经分派的消息。当前快照也不等于历史记录：不同的摸切顺序可能产生相同的手牌与牌河，无法仅凭最终局面唯一还原。

如果需要随时打开统计窗口查看此前过程，记录器应在牌局开始前就运行并持续落盘。首次启动发生在局中时，必须以实际收到的恢复数据确定可恢复范围。

## 当前实现如何标注恢复状态

[core.cjs](../src/core.cjs) 将 `handComplete` 与 `historyComplete` 分开记录。其中 `historyComplete` 只涉及当前小局的动作连续性，不代表整场比赛、所有协议字段或隐藏信息都已完整。

| 基线 | 当前行为 | 完整性说明 |
| --- | --- | --- |
| `new_round` | 从发牌建立手牌、牌河、副露等状态，再连续应用动作 | 收到起手牌时可标记手牌完整；漏步、解析异常、未知动作或更新不一致会取消完整标记 |
| `restore_actions` | 找到恢复动作列表中最后一个开局，从该位置回放 | 保留“恢复响应边界待现场核对”警告，并将 `historyComplete` 设为 `false` |
| `snapshot_unverified` | 展示恢复快照中的手牌和公开状态 | `handComplete` 与 `historyComplete` 保持 `false`，不将快照当作已确认的连续手牌基线 |
| 没有独立可用的基线 | 显示已知消息及缺失提示，等待新的基线 | 不宣称当前手牌或历史完整 |

恢复响应只输出一次恢复后的当前状态，不逐条刷新历史面板。断线时已有统计标记为可能过时；切换牌局连接时重新建立状态，避免把不同连接的动作混在一起。

需要继续核对的恢复细节包括：响应动作序号与快照时间点的关系、补发动作位于快照之前还是之后、特殊弃牌编码、被鸣走的弃牌标记，以及只返回增量而没有独立基线的情况。协议中存在快照或动作列表字段，并不保证每次响应都填满这些内容，也不保证返回整场比赛。

## 验证与维护

测试入口为工程根目录的 `./scripts/test.sh`。固定原始消息和对应动作样本保存在 [tests/fixtures/recording](../tests/fixtures/recording)，测试包括：

- 真实样本中的动作、座位、牌值和可见性对应关系。
- 新小局基线、重复动作去重、动作缺口、立直成立及结束重置。
- 实时动作还原与恢复动作明文解码的区别。
- 原生消息桥接、静默日志，以及浮层布局、点击穿透和清空。

这些检查用于验证当前实现和已有样本，不替代“任意时刻完整恢复”的真实对局验收。后者需要在可控测试对局中同时保留从开局开始的参考记录，捕获局中正常恢复响应，逐项比对手牌、牌河、副露、分数、宝牌、剩余牌数及动作顺序，再判断具体响应能够保证的范围。

构建和打包后的离线验证命令见 [README](../README.md)，普通使用见 [使用说明](使用说明.md)。
